## 2026-06-12 比赛安全链精简决策

```text

  -> TaskQueue
  -> Operator execution_enabled

  -> Unitree chassis
```

- LLM 只做意图、目标和任务拆解，不决定安全阈值。

- Python `gateway_safety.py` 只读取 Gateway 的 `allow_navigation/reason`。
- SlamGateway 是唯一运动安全权威，运行中 watchdog 负责暂停。
- XT16 五场标定、地图/PCD 哈希和 Git 绑定保留为赛前验收工具，不进入比赛主 UI。

持续性检查发现旧 `ptp4l` 参数会周期性出现 `timed out while polling for tx
timestamp`；进程仍存在，但雷达从 `Locked` 退回 `Free Run`。根因是机器人
`eth0` 只提供软件时间戳，而默认 10 ms 发送时间戳等待不足。设置
`--tx_timestamp_timeout 1000` 后实机连续 120 秒保持 `Tracking/Locked`，只有
一个 PTP 进程，偏差保持纳秒级。manager 现要求连续 5 个健康样本，并在 SLAM
启动前 fail-closed 检查。

正式部署后的启动复验还观察到：`xt16_driver` 初始化期间雷达曾短暂显示
`Free Run`，但 `ptp4l` 日志没有发送失败，雷达随后自行恢复 `Tracking`，正式
点云持续发布。为避免把正常重新捕获误判为持续失锁，运行时 `check` 在最多
`20 s` 内等待连续 5 个健康样本；窗口结束仍为 `Free Run` 才返回失败。

XT16 不需要互联网授时。它是独立设备，不会自动读取 Linux 系统时钟；离线正确
链路为 `机器人系统时钟 -> eth0 本地 PTP master -> XT16`。如果机器人系统时间
本身错误，雷达也会跟随错误时间。

历史撞箱子不能归因于本次时钟问题。时钟失同步可直接阻断点云与重定位，但
2026-06-01 事故已有明确原因：固定 `6.0m` 占位值被信任、缺少左右近障检查、
错误导航模式和暂停闭环不完整。
